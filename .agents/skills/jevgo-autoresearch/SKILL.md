# JevGO autoresearch 项目记忆

## 先读取目标，再定位任务

进行适用的设计、代码修改或算法评审前，读取 [项目目标与实验协议](references/project-goal.md)。它记录用户已经确定的目标、核心循环及建议的实验设计；不要将建议或规划当作已有实现或实验结论。

JevGO 的研究问题是：在模型参数冻结、环境交互和推理成本可核算的条件下，LLM 提议、JEV 评估与 MCTS 搜索能否提高自动研究和交互任务的成功率与证据质量。模型版本和路径以项目 `configs/jevgo.yaml` 及资源清单为准，实际能力以代码和验证记录为准。

在首次修改前，用一段简短 commentary 给出本次定位：

> 本次实现/评审：AR-x「环节名」（必要时列出关联环节）；目标：……；输入 → 输出：……；上下游：……；验证：……；对默认无训练模式、接口与公平对比条件的影响：……。

定位是工作说明，不是审批请求。能够从任务和代码推断时直接决定并继续；跨多个环节时列主环节及受影响环节，不强行归为一个。未澄清的实质研究目标冲突才需要询问用户。

## 稳定的流程编号

| 编号 | 环节 |
| --- | --- |
| AR-0 | 定义问题、成功条件和预算，初始化显式状态 |
| AR-1 | 按搜索统计选择待扩展节点或分支 |
| AR-2 | LLM 提议候选，JEV 评估合理性与优先级 |
| AR-3 | 将研究意图具体化为可执行实验或动作 |
| AR-4 | 在对应的真实环境分支执行并记录原始反馈 |
| AR-5 | 整理证据、保留有用发现并生成后继状态 |
| AR-6 | 评估后继状态/叶节点，沿搜索路径回传统计 |
| AR-7 | 判断完成或预算耗尽，继续搜索、提交动作或输出答案 |

训练扩展标记为 `TRAIN`，对比与评测协议标记为 `EVAL`；同时注明它影响的 AR 环节。文件位置不能代替语义定位。

## 适用边界

- 修改状态含义、搜索树、候选生成/剪枝/排序、JEV 评分接口、实验规划、分支管理、证据记忆、回报/价值回传、停止条件、推理预算或研究消融时，执行上述定位。
- 普通依赖维护、离线包迁移、模型下载、排版以及任务专用求解器内部算法，不要求完整 AR 定位。不要将一切算法都称为 autoresearch 算法。
- 单个 benchmark 适配或工具实现若保持既有框架契约，只简述它支撑的环节；若改变观测、动作粒度、克隆/重放、成功信号或环境调用计数，则按相应 AR 环节/EVAL 定位。
- 修改代码、测试和脚本时继续遵循仓库 `AGENTS.md` 中的发布目录规范；本技能不替代该规范。

## 实现与收尾

执行依赖 GPU 的真实生成/评分、测试或 EVAL 前，先读取 [GPU 访问与沙箱排查](../jevgo-gpu-access/SKILL.md)，区分设备访问、runtime、显存容量与模型执行问题；排查本身不改变默认无训练模式或实验条件。

1. 先核对相关代码、配置和近期验证记录，明确“已有能力”与“本次新增”，避免从规划反推实现状态。
2. 保持默认 `learning_mode: none`；MCTS 的节点访问数和价值统计、研究状态与记忆可以更新，模型参数不训练。
3. 保持实际观测、假设、推导及评分可区分；保留原始证据与分支来源。不能用 JEV 的意见替代环境事实、终局信号或客观评测。
4. 根据本次定位验证有意义的行为，例如证据来源、分支隔离、回传路径、预算计数或终止原因；文档变更只需检查结构、一致性和引用。
5. 完成时说明实现了哪些 AR 环节、验证了什么、哪些仍未实现。持久设计变化更新目标参考，具体实验/调试记录按发布目录规范放开发区；不要把临时结果堆进长期记忆。
