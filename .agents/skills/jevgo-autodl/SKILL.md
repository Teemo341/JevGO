# JevGO AutoDL 备用 GPU

把原计划在本地运行的模型实验移到用户提供的 AutoDL，取得结果后继续在本地分析和编程。
这是 JevGO 项目技能；先定位当前 JevGO 工作树，不把其他项目当作默认目标。
本技能不自动创建云实例或保存平台镜像。

## 先决定是否需要 AutoDL

真正加载模型到 GPU 前，按 [GPU 访问技能](../jevgo-gpu-access/SKILL.md) 检查本机；沙箱看不到设备不等于资源不足。
记录 `hostname`、每张卡的 UUID/型号、总/剩余显存、利用率及 GPU 进程，保留 `CUDA_VISIBLE_DEVICES` 的原有约束。
可用 `nvidia-smi` 的完整进程表，加 `--query-gpu=index,uuid,name,memory.total,memory.free,utilization.gpu --format=csv` 和
`--query-compute-apps=gpu_uuid,pid,process_name,used_memory --format=csv`；需要时核对进程所有者。
“空闲卡”指没有正在使用该卡的 GPU 任务，不是仅功率低或还能挤入一些显存；不能终止他人的进程。

| 任务 | 本地选择 |
| --- | --- |
| 只查驱动/CUDA、编译或 CPU 测试，不加载模型到 GPU | 不触发 AutoDL 流程 |
| 简单 demo，显存需求确实很小 | 在允许使用的卡中选剩余显存最多且足够的一张，不打断现有任务 |
| 4B 或 9B LLM | 至少一张空闲卡，且足够容纳实际配置 |
| 27B LLM（含 VL） | 至少两张空闲卡，且实验实现支持对应的多卡方式 |

本地满足条件就直接本地执行，不申请 AutoDL、不为此 push。启动模型前再检查一次实时占用。
卡数只是最低门槛；结合精度、上下文、batch、KV/优化器开销和实际并行能力核实容量。
27B 即使本地仅有一张大显存空闲卡，也按用户规则转入 AutoDL；这个两卡规则针对本地分流，AutoDL 可用满足任务需求的一张 96 GiB 卡。
其他规模按实际需求判断，不擅自更换模型、量化、精度或实验条件。

## GitHub 与申请实例

确认需要 AutoDL 后，**先把本地已保存、可公开的项目修改提交并 push 到 GitHub，再询问 SSH 登录方式**。
检查工作树和 diff，使用明确文件清单提交可发布源码、配置和测试；不使用无审查的 `git add -A`。
不提交凭据、权重、环境、离线二进制、实验输出，也不擅自发布来源不明或其他任务的未确认修改。
已有相关提交同样要推送。保留当前分支，常规非强制 push，核对远端分支 SHA 等于本次提交；不为实验强推或合并到 main。
本次授权覆盖这个 GPU 回退流程中的普通提交/push，无需反复申请；编写/维护本技能本身不触发 push。
推送失败先修复或说明阻塞，不把未成功的 push 当作完成；不要让用户提前开机付费等待源码准备。

询问用户时说明任务、建议 GPU/显存、所需磁盘余量，收集免密 SSH 的主机、端口、用户名，例：
“本机仅有一张空闲卡，不满足这次 JEV-27B 的两卡规则。请开启同一 NAS 的 AutoDL GPU 实例并提供 SSH 命令；本次需要……”。
不要索取密码、私钥或在远端存 GitHub push 凭据。用户提供当前有效连接后继续执行，同一实例无需重复申请。
历史端口不能当作新实例地址；若已有明确有效的本轮实例，可直接复用。

## 只在 AutoDL 执行生命周期脚本

**`prepare.sh`、`monitor.sh`、`shutdown.sh` 全部是 AutoDL 上的脚本，绝不能在 105 上运行；本地机器绝不能关机。**
本地仅执行 Git、SSH、rsync、源码打包和结果分析；通过 `ssh ... '远端命令'` 执行这三个脚本。
不要沿用旧的 `prepare.sh --host ...`、`monitor.sh --host ...`、`shutdown.sh --host ...` 本地控制方式。

按 [AutoDL 操作说明](../../../.dev/tools/autodl/README.md) 的“远端入口部署与身份核对”及相应命令执行：

1. 核实本轮 SSH 目标不同于本机；检查 `autodl-container-*` 主机名、地址不含 `10.200.48.105`、AutoDL PID 1 和真实挂载。
   使用 `BatchMode=yes`、`ForwardAgent=no`，保留/校验 SSH 主机密钥，不用关闭主机密钥检查来忽略变化。
   从用户的 SSH 命令解析参数，不把整段输入交给 `eval`。向脚本传入本地主机名 `--forbid-hostname`。
2. 核对 `/opt/jevgo-autodl` 中为当前远端入口；旧镜像缺少文件时，仅经 SSH/rsync 部署明确的控制文件。
   三个入口在主机核验通过前不写文件、不 source runtime、更不清理 Git 或关机。
3. 在 AutoDL 运行 `prepare.sh --run-id TASK --branch BRANCH --expected-commit COMMIT ...`。
   它检查 GPU/NAS，fetch 指定 GitHub 分支并核对 commit，备份后以该 commit 强制恢复远端源码，再应用本轮明确文件覆盖，最后校验模型链接和环境。
   依赖未变且检查通过直接复用环境；缺包或依赖变化才补装。报告 `needs_materials` 时，仅传清单要求的 wheel 到高速盘，再用 `--resume` 继续。
   保留本机离线材料；成功安装后删除远端临时包。缺少材料或 ABI 不匹配时先修复，不重装整个环境。
4. 只有本次任务确有未发布修改时才补传：逐项列出文件/删除项，用 `pack_overlay.py` 在本地打包，经 rsync 上传，给远端 prepare `--overlay`。
   禁止整仓 rsync 覆盖、`rsync --delete` 或自动同步全部本地脏文件。每轮新 prepare 都先让远端源码以 GitHub 为准（`fetch`、`reset --hard`、精确清理新增源码），然后应用本轮覆盖；不需要上一轮覆盖编号。必须先取回有价值的远端调试修改和小日志；容器内自动源码备份不等于已取回。环境、模型链接、产物与 NAS 受保护；有 GPU 进程或保护路径冲突时停止，不强制关闭任务。`--resume` 仅继续同一源码包的补包阶段，不重新恢复源码。
5. 在 AutoDL 测量当前无任务时的功率，给 `monitor.sh` 明确的 `--idle-watts`，再后台启动监控并确认 PID/首个采样正常。
   默认每 30 秒采样，**所有卡低功率且没有 GPU 计算进程连续 30 分钟**才调用远端清理关机。
   有 GPU 进程即使功率很低也不关机，计时重置；读数失败/异常也重置，不视为空闲。
   以前 96 GiB RTX PRO 6000 的 45 W 阈值仅是该实例实测参考，不能套用所有卡。
   用户明确要求保持开机的镜像联调轮次，不开启自动关机；先停止本任务已启动的 monitor。

## 远端实验与存储

通过 SSH 在 `/root/JevGO`、已验证的运行环境中运行原实验，使用明确的 GPU 选择、命令、随机种子和 `run_id`。
不要把 prepare 的微型 CUDA 检查当作真实模型实验已通过，也不要为速度改变实验契约。

| 位置 | 用途与限制 |
| --- | --- |
| `/root/JevGO`（`~/JevGO`，系统/镜像盘约 30 GiB） | 代码、uv/Python/Java、`.venv`，小日志可直接保存在项目相对路径 |
| `/root/autodl-tmp`（约 50 GiB） | 安装临时包、缓存、临时数据，视作关机/新实例后不可恢复 |
| `/root/autodl-fs`（NAS 约 200 GiB） | 原始权重和经用户指定的训练权重输出；持续计费 |
| `/root/JevGO/models` | 整体软链接到 `/root/autodl-fs/JevGO/models` |

全部 4B/9B/27B 原始权重复用同一 NAS，不从 HF/镜像站重新下载，也不在训练结束删除。
仅首次/变化时按清单完整校验哈希与分片索引；`models ensure` 在可信校验记录、挂载身份和元数据一致时复用结果。
不能覆盖真实非空模型目录。GitHub 联网可以 `source /etc/network_turbo`，仅在 AutoDL 的联网进程中使用。
保留已验证的 CUDA 12.8/12.9 工具链，LoRA 保持 FP32，除非本次用户另行指定。

**将产生 checkpoint/模型权重的训练，在开始前确认用户指定的 NAS 输出位置和所需容量。**
当前没有统一授权的新输出位置，不擅自采用旧任务目录；询问可与 SSH 连接问题一起提出。
先核实 NAS 真实挂载及余量，在项目中建立指向该专用 NAS 目录的软链接，再把训练保存路径设为此链接。
即使结果预计很小，也按权重产物处理；禁止先写入 30 GiB 系统盘再搬运，不覆盖原始共享模型。
NAS 不可用时停止保存，不能静默写到根盘；保存后记录大小、SHA256 和必要的索引/重载验证。
这些权重留 NAS，用户后续安排传回；不自动下载整个 checkpoint 到本机。

小日志、JSON 报告、stdout/stderr 和评测结果写项目内受清理保护的 `.dev/artifacts/<任务>/` 或 `.dev/logs/<任务>/`，**不要放 NAS**。
实验结束（包括失败）立即通过明确文件清单取回本机**相同相对路径**，核对大小/哈希；不能递归跟随 checkpoint/model 软链接。
取回退出码、实际代码版本/覆盖哈希、执行配置和产物清单，随后在本地分析。
远端 monitor 不向 105 传日志，不能把容器内备份当成已取回；自动关机前应及时完成取回。
GPU 阶段后的长时间 CPU 分析取回所需文件后在 105 完成，不依赖 GPU 空闲来判断整个实验已结束。只有用户明确要求远端继续后处理并保持开机时才暂停本任务 monitor。105 断连时监控仍会计时，不能保证未回传小文件的持久保存。

## 分析后决定是否关机

结果符合本次预期，或接下来要分析/编程较久、预计超过 30 分钟不用 GPU：取回日志与有价值的远端调试修改，确认 NAS 权重完好，**经 SSH 在 AutoDL 运行 `/opt/jevgo-autodl/shutdown.sh`**。
结果需 debug/小改且预计半小时内还要 GPU：保持实例和监控，先本地修改，再按明确文件更新并复测。
用户明确要求暂不关机时以其指令为准；不要因加载慢就擅自关机。

shutdown 先复核实例、空闲进程和源码计划，撤销远端 tracked/staged 修改，按精确清单清理新增源码，再执行 AutoDL 平台关机。
保护 `.venv`、工具、模型链接、缓存、审计和 NAS 产物，不用 `git clean -x/-X`。
有 GPU 进程、未知代码冲突或身份/挂载异常就停止，不强制杀进程/关机。
源码备份默认仍在 AutoDL 容器盘，不能替代关机前取回本地的调试补丁。
确认脚本已发出平台关机请求，再检查 SSH 不可达；SSH 断开本身不等于成功关机，也不代表镜像已保存。

向用户报告本地/远端选择依据、实际测试版本和结果、本机日志位置、NAS 权重位置，以及 AutoDL 保持开机/已请求关机/状态未确认。
